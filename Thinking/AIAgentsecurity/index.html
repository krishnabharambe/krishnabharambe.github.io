THINKING / AI SECURITY

Securing AI agents:
identity, tools, and control.

An AI agent is more than a model response: it can hold context, call tools, and cause changes. Secure it like a real actor—with an owner, a bounded identity, controlled capabilities, and an auditable lifecycle.

An AI agent can combine a model, prompts, memory, tools, credentials, and access to business systems. Security depends on governing that complete system—not just the model.

The useful IAM question is not only “Who can sign in?” It is also “Which agent is acting, on whose authority, through which tool, against what resource, and where is that action recorded?”

i

Start with bounded autonomy. Give the agent only the capabilities required for its task. Keep consequential actions reviewable, and make safe behavior the default when identity, policy, or context cannot be verified.

01 / Understand the system

A practical model for an AI agent

Before selecting controls, map the components and trust boundaries. These parts may be operated by different teams and should not be treated as one shared identity.

01Model

Produces outputs from instructions and supplied context.

02Agent runtime

Maintains task state, selects actions, and coordinates execution.

03Tools

Expose specific operations such as search, read, update, or submit.

04Identity & credentials

Establish who or what is acting and which authority it receives.

05Data & memory

Provide the context an agent can retrieve, retain, or pass onward.

06Owner & operator

Are accountable for purpose, permissions, review, and retirement.

Each connection is a security boundary: user-to-agent, agent-to-model, agent-to-tool, tool-to-resource, and runtime-to-memory. Document those flows, data types, identities, and failure behaviors before granting production access.

02 / Establish accountability

Give each agent a distinct identity

An agent that acts against enterprise resources should be attributable to a specific workload identity and accountable owner. Avoid shared credentials that make unrelated agents indistinguishable.

RecordGovernance purpose
Stable agent IDDistinguishes this agent from its model, tools, users, and other workloads.
Owner and sponsorNames the team responsible for purpose, permissions, review, and retirement.
Business purposeDescribes the approved use case and intended operating context.
EnvironmentSeparates development, test, and production identities and access.
Authority modelRecords whether actions use workload authority, delegated user authority, or an approved combination.
Lifecycle stateSupports activation, suspension, review, expiry, and decommissioning.
Connected tools and dataShows the capabilities and resource boundaries available to the agent.
Review historyRecords approvals, access reviews, changes, and material incidents.
!

Delegation needs boundaries. If an agent acts for a user, scope the delegation to the task, resources, and duration. Do not silently turn a user request into broad, reusable agent authority.

03 / Limit blast radius

Apply least privilege to every run

Least privilege applies to the agent identity, the user delegation, each tool, and the resources behind the tool. A model’s ability to suggest an action is not itself authorization to perform it.

01

Separate read and write. Start with read-only capabilities; grant changes only where the use case requires them.

02

Scope to resources. Restrict access to the required tenant, project, records, or data classification.

03

Use short-lived authority. Obtain credentials for a specific task and expire or revoke them promptly.

04

Keep environments apart. Do not reuse development or test credentials in production.

05

Review privilege changes. Reassess permissions when tools, models, prompts, owners, or purposes change.

Where delegated access is available, prefer explicit and narrow authorization over storing a person’s long-lived credentials in an agent runtime.

04 / Put policy between reasoning and action

Constrain tools and side effects

Tools are where an agent’s reasoning can become an external effect. Treat every tool as a privileged interface with a documented owner, authorization policy, input contract, and audit trail.

ALLOWNamed operations

Expose purpose-built actions instead of broad, unrestricted interfaces.

CHECKAuthorization

Enforce policy in the tool or service, not only in a prompt.

VALIDATEArguments

Verify types, formats, resource ownership, and allowed values.

LIMITRate & scope

Cap operation volume and bound accessible resources.

SEPARATEPreview & commit

Make consequential changes an explicit, reviewable step.

RECORDTool results

Capture actor, authorization, target, outcome, and correlation ID.

Prefer safe, narrow functions that represent approved business actions. Avoid giving an agent general-purpose access to a shell, database, or administrative API when a bounded operation will meet the need.

05 / Keep data separate from authority

Treat retrieved content as untrusted input

Agents may process documents, messages, web pages, tickets, or tool output that contain misleading instructions. That content can inform a task, but it must not grant permissions, override policy, or authorize a tool action.

01

Preserve trust labels. Track whether context came from a user, a trusted system, or an external source.

02

Keep policy outside retrieved content. Authorization should be enforced by trusted code and services.

03

Verify before acting. Re-check user intent, resource scope, and permissions at the tool boundary.

04

Minimize context. Retrieve only the information required for the current task and respect source access controls.

05

Handle uncertainty safely. Pause or request review when a source, instruction, or intended action is ambiguous.

Instruction hierarchy can help guide model behavior, but it is not a substitute for enforcing access control independently of the model.

06 / Contain failures

Isolate execution and restrict connectivity

Run agent workloads with explicit resource limits and a clear boundary between the runtime and the host or other workloads. Isolation reduces the consequences of unexpected behavior, vulnerable dependencies, and compromised components.

  • Use a dedicated, maintained runtime with only the components the agent needs.
  • Restrict filesystem access and avoid exposing host credentials or unrelated workloads.
  • Use controlled network egress and allow only required destinations where practical.
  • Set limits for runtime, memory, concurrency, and tool-call volume.
  • Separate development, staging, and production environments and their data.
  • Provide a clear way to stop an agent and revoke its active authority.

Choose isolation controls appropriate to the sensitivity of the data and the potential impact of the actions. Isolation is one layer, not a reason to grant extra privileges.

07 / Protect sensitive material

Protect data, memory, and credentials

Agent context and memory can accumulate sensitive business or personal information. Define what may be collected, retained, searched, and shared, and enforce the same data-access rules across retrieval and tools.

AreaDefensive practice
CredentialsUse an approved secret manager or workload identity; never place secrets in prompts, source control, or general conversation logs.
RetentionSet purpose-based retention and deletion for prompts, traces, memory, and intermediate artifacts.
RetrievalEnforce the requesting user’s or workload’s access policy when fetching source data.
Training and reuseDefine whether submitted data may be used for model improvement or later tasks.
LoggingRedact or minimize sensitive values while preserving enough metadata for oversight.
MemoryMake persistent memory scoped, reviewable, correctable, and removable when no longer needed.

08 / Match autonomy to impact

Use human approval for consequential actions

Approval should depend on the action’s impact and reversibility—not simply on whether an AI is involved. A low-risk lookup may be automated; a sensitive or hard-to-reverse change deserves stronger controls.

LOW IMPACTRead or summarize

Automate within authorized read scope; retain traceability.

MODERATE IMPACTPrepare a change

Generate a preview and require the appropriate person to confirm.

HIGH IMPACTPrivileged or irreversible

Require explicit authorization, policy checks, and a clear recovery plan.

Show the reviewer what will change, why the agent proposes it, which identity will act, and the scope of the action. Keep approval separate from the content being processed so untrusted data cannot approve itself.

09 / Know what happened

Make actions observable and auditable

Useful records connect a human request to an agent run, the identity and delegated authority used, each tool decision, the target resource, approval, and final outcome. Consistent correlation IDs help connect logs across services.

LOG

Security-relevant events. Record identity issuance, permission changes, tool calls, approvals, policy denials, and lifecycle changes.

PROTECT

The audit trail. Limit access, set retention, and protect logs from unauthorized alteration.

ALERT

Meaningful deviations. Surface unusual volume, out-of-scope attempts, repeated denials, and unexpected privilege use.

RESPOND

Contain and recover. Assign incident ownership and practice pausing runs, revoking access, and reviewing affected resources.

Do not log credentials or sensitive payloads by default. Capture the minimum evidence needed to investigate while respecting privacy and data-handling requirements.

10 / Validate the system, not just the model

Test security across the full lifecycle

Evaluate expected behavior and failure behavior before release and after meaningful changes. Include the runtime, identity provider, tools, data sources, policy enforcement, human workflow, and monitoring in scope.

  • Verify that each tool enforces the intended identity and resource permissions.
  • Confirm that denied, expired, or missing authorization fails closed.
  • Check that agent identity and user delegation remain distinguishable in records.
  • Test how the system handles conflicting instructions and untrusted retrieved content.
  • Review data access, retention, deletion, and redaction behavior.
  • Exercise approval, cancellation, timeout, revocation, and recovery flows.
  • Reassess after changing models, prompts, tools, permissions, or connected data.

Use controlled environments and synthetic or approved test data. A passing model evaluation alone does not prove the surrounding access controls are effective.

11 / A practical adoption path

Roll out in stages

01Inventory

Identify agents, owners, tools, data, identities, and environments.

02Start read-only

Validate usefulness and access boundaries before enabling changes.

03Bound the action

Add only specific, policy-enforced operations needed for the use case.

04Review high impact

Set approval and recovery requirements according to risk.

05Monitor and improve

Review events, access, incidents, and changing business needs.

✓

Before production, confirm: every agent has an owner and unique identity; each permission has a reason; tools enforce authorization; sensitive actions are appropriately reviewed; and the team can audit, pause, and retire the agent.

THE SECURITY PRINCIPLE

Autonomy should never be unaccountable

Secure AI agents by making identity explicit, authority narrow, tool actions policy-controlled, execution contained, and outcomes reviewable. Increase autonomy only when the controls and evidence support it.

This is a defensive starting point, not a substitute for a threat model, privacy review, or the requirements of your organization and industry.
