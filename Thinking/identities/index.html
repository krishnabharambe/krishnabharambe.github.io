Complete guide to
identity types in IAM.

People, applications, workloads, devices, and AI agents all need the right identity—and the right level of access. Here’s a practical way to classify and govern them.

In Identity and Access Management (IAM), an identity represents a person, system, application, device, workload, or other entity that can authenticate, receive permissions, or perform actions.

For modern IAM, a useful starting point is to group identities into human, non-human, and AI identities. Federation, external access, and privilege add important context around those groups.

i

These categories overlap. A cloud service account can be non-human, privileged, federated, and orphaned at the same time. Treat identity type as one attribute—not as a mutually exclusive classification.

01 / Start with the entity

A practical identity model

Start by identifying what is acting, then describe how it is owned, authenticated, and authorized. This keeps a person’s identity separate from the accounts they use and the access assigned to those accounts.

01Who or what?

Person, application, workload, device, AI agent, or another entity.

02Who owns it?

An accountable person or team, plus an authoritative source.

03What can it do?

Accounts, credentials, roles, entitlements, and delegated authority.

04Is it still needed?

Lifecycle status, review history, risk, and a clear end-of-life.

03 / Software, infrastructure & machines

Non-human identities

Non-human identities (NHIs) are used by software, infrastructure, automated processes, and machines rather than directly by people. They often run unattended, which makes accountable ownership, credential handling, and lifecycle tracking especially important.

A

Application identities

  • Application registrations and enterprise applications
  • Service principals and application service accounts
  • OAuth clients and API clients
  • Integration accounts and middleware identities
  • Microservice identities
B

Infrastructure & workload identities

  • Virtual machines and server identities
  • Container identities and Kubernetes service accounts
  • Cloud workload and managed identities
  • Serverless function identities
  • CI/CD pipeline and build-agent identities
  • Infrastructure-as-code automation identities
  • Federated workload identities
C

Data & database identities

  • Oracle, MySQL, PostgreSQL, and SQL Server accounts
  • Snowflake users and service users
  • Data warehouse service accounts
  • ETL, data integration, and data replication identities
  • Backup, recovery, and database automation accounts
D

API & integration identities

  • API keys associated with a client or application
  • OAuth client-credentials identities
  • Integration-platform accounts and ETL connectors
  • Webhook delivery and API gateway service identities
  • Robotic Process Automation (RPA) bots and scheduled jobs
  • File-transfer and cross-system synchronization accounts
E

Device identities

  • Employee laptops, desktops, and mobile devices
  • Servers and network appliances
  • IoT sensors and industrial OT devices
  • Printers and security cameras
  • Device certificates and machine credentials

04 / A growing class of actors

AI identities & autonomous agents

AI identities deserve explicit treatment when agents can call tools, access data, or perform actions. An agent’s authority should be defined, limited to what it needs, and reviewable after use.

Identity typeExample
AI agentAn autonomous IT support agent
AI assistantAn enterprise copilot
Multi-agent systemA coordinator agent managing several agents

!

Keep the actors distinct. The AI model, the agent running the model, the tool it calls, and the service account it uses may be separate entities. They should not automatically share one identity or one set of permissions.

06 / From inventory to governance

What should an IAM engineer collect?

When building an identity collector across infrastructure, databases, cloud platforms, applications, and AI workloads, capture enough context to establish ownership, evaluate access, and manage change over time.

01

Identity type — human, application, workload, device, AI agent, or another useful classification.

02

Unique identifier — an immutable identifier from the authoritative source.

03

Owner — the person or team accountable for the identity.

04

Source system — Workday, Active Directory, AWS, a database, or another system of record.

05

Entitlements — groups, roles, permissions, policies, and access assignments.

06

Authentication — password, certificate, federation, managed identity, or token; never collect secret values in an inventory.

07

Lifecycle — active, inactive, pending, expired, or decommissioned, with relevant dates.

08

Privilege & risk — privilege level, sensitive access, SoD violations, and risk findings.

09

Relationships — parent application, associated workload, human sponsor, delegated authority, and connected resources.

07 / The essential distinction

An identity is not an account

An identity is not the same thing as an account, a credential, or an entitlement.

Identity→Accounts→Credentials+Entitlements

A person may have multiple accounts; an account may use several credentials; and each account may have many entitlements. Keeping these concepts distinct is fundamental to building an accurate IGA or identity-security platform.
